# Production Data Isolation And Clean Baseline

This runbook and evidence record belongs to the completed owner-approved **Production Data Isolation & Clean Baseline** sprint. It records observed results only.

## Safety Invariant

Ordinary automated regression testing must fail closed before writing or deleting data when its database target is the real WeatherTech OS production project. Production credentials, localhost, synthetic-looking content, or a test-name prefix do not authorize production mutation.

A purpose-built production validation is separate from ordinary regression. It requires explicit owner authorization for the exact mutation, company, target, and limit; it must not provide a general production override to seed or cleanup code.

## Implemented Isolation Contract

- Guard: `tests/codex-browser/regression-target-guard.mjs`, called by `tests/codex-browser/weathertech-os-regression.mjs` before its first database read, seed, or cleanup.
- Automated coverage: `tests/browser-regression-isolation.test.mjs`; the final focused run passed.
- Application boundary: the data-writing suite accepts only a locally served app URL.
- Local target: local Supabase is allowed with a recognized service-role credential.
- Hosted non-production target: both `WTOS_BROWSER_REGRESSION_REMOTE_WRITES_ENABLED=true` and `WTOS_BROWSER_REGRESSION_EXPECTED_PROJECT_REF=<exact non-production project ref>` are required, and a decodable service-role JWT must match the URL project reference.
- Production detection: the hosted URL project reference is checked against the immutable WeatherTech production reference and the repository's linked Supabase reference. A known production reference is permanently rejected even if both hosted-test authorization values are supplied.
- Cleanup scope: every run uses an exact millisecond-resolution marker, refuses a pre-existing marker collision, verifies residue, and refuses Stripe-linked payments or mappings.
- Purpose-built production-validation boundary: no ordinary browser-regression override can authorize the known production project. An owner-approved production validation must use its separate application workflow.

The guard executes before the harness performs any database read, cleanup, or seed. Cleanup remains bounded to the exact current-run marker and target established by that preflight. If future code permits a target to change during a run, it must re-verify identity at the mutation boundary.

## Synthetic Classification Standard

A record may be classified as synthetic only when evidence establishes its test origin. Applicable evidence can include:

- an exact marker or external ID generated by the regression harness;
- a known run ID linked to records created by that run;
- a deterministic test-name pattern combined with matching creation relationships and timestamps;
- source, metadata, integration-log, webhook, payment, invoice, or foreign-key relationships that trace to the authorized test;
- an exact identifier captured by the test during creation; or
- another independently verified provenance signal.

An unusual amount, missing customer, old timestamp, test-like label, or aggregate anomaly by itself is not sufficient. If evidence conflicts or a legitimate-business origin remains possible, classify the row as uncertain and leave it unchanged.
